## F1 — Version drift between CMake and README (confirmed)

- `CMakeLists.txt:2` → `project(tazvera_chain_core VERSION 0.8.2 LANGUAGES CXX)`
- `README.md:1` → `# TAZVERA Chain — Core v8.8`

The CMake version has been stale for six releases. It is not cosmetic: anything that reads the binary version (packaging, a future `--version` flag, an auditor asking "which build is this?") will report `0.8.2` for a v8.8 binary.

**Proposed change — one source of truth.**

1. In `include/taz/types.hpp`:

```cpp
// v8.9: the one place the version lives. CMake reads this line (see CMakeLists.txt) and the test suite
// compares it with the README title, so the three can no longer drift apart.
inline constexpr std::string_view CORE_VERSION = "8.9";
```

2. In `CMakeLists.txt`, replace the hard-coded version:

```cmake
file(READ "${CMAKE_CURRENT_SOURCE_DIR}/include/taz/types.hpp" TAZ_TYPES_HPP)
string(REGEX MATCH "CORE_VERSION = \"([0-9]+\\.[0-9]+)\"" _m "${TAZ_TYPES_HPP}")
set(TAZ_CORE_VERSION "${CMAKE_MATCH_1}")
if(NOT TAZ_CORE_VERSION)
    message(FATAL_ERROR "CORE_VERSION not found in include/taz/types.hpp")
endif()
project(tazvera_chain_core VERSION ${TAZ_CORE_VERSION} LANGUAGES CXX)
```

3. A test (`t15_version_consistency` in `tests/test_persist.cpp`, which already reads repository files through `TAZ_SOURCE_DIR`) that asserts the README's first line contains `CORE_VERSION`. A drifted README then fails CI instead of surviving a review.

**Cost:** ~15 lines. **Risk:** low. The CMake `project()` call must stay before `find_package`, so the version block moves to the top of the file.

## F2 — `sweep_stale_temp_files()` runs outside the try/catch (confirmed)

`src/persist.cpp:422-427`:

```cpp
bool save_chain_json(const Chain& chain, const std::string& path, std::string* error) {
    auto set_err = [&](const std::string& m) { if (error) *error = m; };
    if (chain.blocks().empty()) { set_err(...); return false; }
    sweep_stale_temp_files(path);   // ← line 425, BEFORE the try
    static std::atomic<unsigned long> counter{0};
    std::string tmp;
    try {                            // ← line 427
```

The function body uses `std::error_code` overloads everywhere, so the common failures cannot throw. But three things in it can: `path_from_utf8()` (allocates a `std::filesystem::path`, and on Windows performs a UTF-8 conversion), `target.filename().string()`, and `std::chrono`/`directory_iterator` construction. Any of those throwing `std::bad_alloc` or `std::filesystem_error` escapes `save_chain_json`, which the header documents as "Returns false and sets `*error` on any problem". A save that throws is a save a caller cannot handle.

**Proposed change — belt and braces, both cheap.**

1. Move the call inside the existing `try` block (one line moves).
2. Mark the helper `noexcept` and give it its own catch-all, so even a future edit cannot let it escape:

```cpp
void sweep_stale_temp_files(const std::string& path) noexcept {
    try {
        ... existing body ...
    } catch (...) {
        // Housekeeping must never break a save. A stale file that survives is not an error.
    }
}
```

**Test:** `t16_save_never_throws` — call `save_chain_json` with a path inside a directory that exists but is not writable (and with a path that is a directory), assert it returns `false`, sets `*error`, and does not throw. On Linux this also covers the `EACCES` path.

**One more thing found while checking:** the sweep runs on every save and walks the target directory. For a directory with many files that is a small, silent cost on the save path. It is acceptable now, but if the chain file ever lives next to thousands of files, the sweep should be rate-limited (for example, only on the first save per process). Not v8.9 work; recorded here so it is not forgotten.

## F3 — No stale-cleanup test under a UTF-8 path (confirmed)

`t13_non_ascii_path` covers save and load inside `taz-टेस्ट-ü`, but the cleanup tests (`t07`) use ASCII names, so the *combination* — a stale temporary file whose whole path is non-ASCII, cleaned up on the next save — is untested. That combination is exactly where the Windows path conversion could bite, because the sweep builds its prefix from `target.filename().string()`.

**Proposed change — extend `t13_non_ascii_path`:**

```cpp
// a stale temp file next to a non-ASCII target, two hours old, must be swept by the next save
const std::string stale = file + ".tmp.999999.1";
{ std::ofstream out(fs::u8path(stale), std::ios::binary); out << "half written"; }
fs::last_write_time(fs::u8path(stale), fs::file_time_type::clock::now() - std::chrono::hours(2));
CHECK(save_chain_json(c, file, &err));
CHECK(!fs::exists(fs::u8path(stale)));            // swept
{ Chain out; CHECK(load_chain_json(file, out, &err)); CHECK(same_chain(out, c)); }

// and a *young* temp file must be left alone (another process may be writing it)
const std::string young = file + ".tmp.999999.2";
{ std::ofstream out(fs::u8path(young), std::ios::binary); out << "in progress"; }
CHECK(save_chain_json(c, file, &err));
CHECK(fs::exists(fs::u8path(young)));             // not swept
fs::remove(fs::u8path(young));
```

Both halves matter: the first proves cleanup works, the second proves the one-hour guard is real — otherwise a save could delete a file another process is writing.

## F4 — The pin must be described as a plan, not as protection (partly confirmed)

`README.md:247` currently says:

> **Pin preparation** — `LoadOptions::require_genesis_pin` (off by default). A node must never load a chain it cannot identify; the future node binary sets this flag, and a later version makes it the default. Nothing changes for library callers today.

The last sentence is honest, but "A node must never load a chain it cannot identify" describes an intention as if it were a property, and nothing anywhere states what is true today: **the pin is not enforced by anything, because there is no node and no CLI.** A reader skimming the list could conclude that genesis authentication is solved.

**Proposed change — a short plan document plus a rewording.**

1. New file `PIN_ENFORCEMENT_PLAN.md`, four short sections:
   - **Today (v8.9):** the commitment exists and is checked against the file and block 0. `expected_genesis_commitment` exists but no caller sets it. `require_genesis_pin` exists but nothing sets it. **No chain is authenticated today; only tampering is detected.**
   - **v9 (node):** `taznode` takes `--expect-genesis <hex>` or reads it from its config file, and always sets `require_genesis_pin = true`. A node with no pin refuses to start. Tests: missing pin refused, wrong pin refused, matching pin accepted, and a node with a wrong pin never exchanges a block.
   - **v10 (library):** `require_genesis_pin` defaults to `true`; the option becomes "allow an unpinned load" rather than "require a pin", and the loader logs a warning when it is used.
   - **Never:** a pin does not prove that a chain is *good*, only that it is the chain you meant to join. Say so in the document.
2. Reword the README bullet to:

> **Pin preparation (not yet enforced)** — `LoadOptions::expected_genesis_commitment` and `require_genesis_pin` exist, and neither is set by any caller, because there is no node or CLI. Genesis authentication today means tamper detection only; see `PIN_ENFORCEMENT_PLAN.md`. Do not describe this as production security.

**Wording rule for every document from now on:** the phrase "production security" does not appear until there is an audit, a node, and independent validators. Nothing in the repository uses it today; the plan document will say why.

## F5 — Branch protection: there is none (confirmed, and this is the largest risk in the project)

Checked through the API on `aa905f0`:

- `GET /repos/tazvera/tazvera-chain/branches/main/protection` → **403** (not readable with the current token, which is itself a signal that no protection is configured for this app).
- `GET /repos/tazvera/tazvera-chain/rulesets` → **`[]`** — no rulesets exist.

And the history shows the consequence: **PR #14 was merged on 17 November while the `fuzz` check was failing.** The code was fine — the fuzz job had a build error — but the process allowed a red PR to land on `main`. That is the failure mode branch protection exists to prevent.

**Proposal — for you to apply, not for me.** I will not change repository settings. If you want them, these are the exact settings:

*Settings → Branches → Add branch protection rule* (or *Settings → Rules → New ruleset*):

- Branch name pattern: `main`
- ☑ Require a pull request before merging
  - Required approvals: **0** (you are the only reviewer today; raise it to 1 when a second person joins)
  - ☑ Dismiss stale pull request approvals when new commits are pushed
- ☑ Require status checks to pass before merging
  - ☑ Require branches to be up to date before merging
  - Required checks (these are the job names, which is what GitHub matches):
    - `build-and-test` (from *C++ Core CI*)
    - `sanitizers` (from *C++ Core CI*)
    - `windows-mingw` (from *Windows (experimental)*)
    - `fuzz` (from *Fuzz (libFuzzer)*)
- ☑ Require linear history (optional; keeps the log readable)
- ☑ Do not allow force pushes
- ☑ Do not allow deletions
- Leave "Include administrators" **off** while you are the only person, or you will lock yourself out of a hotfix; turn it on when the project has a second maintainer.

*Settings → Actions → General → Workflow permissions*: **Read and write** — required if you ever want an automation (like the cleanup workflow you just ran) to push a commit.

**Two consequences to know before you enable it:** (a) you will no longer be able to push straight to `main`, including from the web uploader — every change will go through a branch and a PR; (b) the Windows and Fuzz jobs must exist on `main` (they do) for their check names to be selectable.

**Note:** the branch name `main` in the check list is the *job* name inside the workflow, not the workflow name. If a job is renamed later, the required check silently stops matching, and GitHub shows the PR as "expected" forever — worth remembering.
